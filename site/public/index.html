Three layers, each with an owner.

Two cipher families and two hash families, one per key, with a layer between them that needs both. If one family weakens in ten years, the other is still standing.

Your record

Layer 1 belongs to the server. AES-256-GCM, under a subkey derived from server_key with HKDF-SHA-512.

Layer 2 belongs to both. Random bytes are woven between the ciphertext bytes at positions only the two keys together can compute. The seed never touches the wire.

Layer 3 belongs to the client. ChaCha20-Poly1305, under a subkey derived from client_key with HKDF-SHA3-512.

The security claim rests on the two standard AEADs. The noise layer is extra depth on top.

Every record gets its own pair.

Your two master keys never encrypt anything directly. Each record derives fresh subkeys from its record_key plus a random 16-byte salt, so one exposed record says nothing about the next. Seal the same record twice and the subkeys still differ.

Questions.

Short answers. The README covers the wire format and threat model in full.

Why two keys instead of one?

So that no single breach exposes your data. Keep one key on your server and give the other to your user, a KMS or a separate service. Reading a record takes both.

What happens if one key leaks?

Records stay sealed, because the other key still protects them. Re-encrypt under a fresh key pair at your own pace.

Is the noise layer homemade cryptography?

The security claim rests on AES-256-GCM and ChaCha20-Poly1305 from pyca/cryptography, both standard and widely reviewed. The noise layer adds depth on top; nothing relies on it alone.

Is it slower than Fernet?

Yes. Sealing a 1 KiB record takes about 27 µs, against 7 µs for Fernet, because it runs two ciphers, three key derivations and the noise layer. Next to a database write, the difference rarely shows.

Can I use a password as a key?

Not directly. Stretch it into 32 bytes with Argon2id first, then pass the result as server_key or client_key.

Does it protect data in transit?

It's built for records and files at rest. Keep using TLS on the wire.

Does it stop replayed ciphertexts?

Not on its own: a valid ciphertext opens every time it's presented. If you need replay protection, put a nonce or timestamp inside the plaintext and track it.

How does it handle large files?

encrypt_stream and decrypt_stream work in 64 KiB frames, so memory stays flat at any size. If decryption fails partway, earlier frames may already be written, so write to a temporary file and rename it on success.
